# ADR 0013: 界面语言与写作协议分开

## 状态
已接受

## 背景

宿主界面文案原先写死在 React 组件里，全部是中文。要给非中文作者用，或以后加第三种语言，不能靠再复制一套组件。

同时，写作协议（思考槽位前缀 `意图：`、标签种类 `人物` / `伏笔` 等）已经进了章节块、导出样本和 Rust 解析器。把这些标识翻译掉会让已有稿件和训练导出对不上。

## 决策

1. **界面语言是前端状态**，不进 SQLite、不走 IPC。存在 `localStorage` 键 `moshu.locale`。设置里可切换；未保存时按系统语言猜（`zh*` → `zh-CN`，`en*` → `en`），否则默认简体中文。
2. **文案目录是类型化对象**，放在 `apps/client/src/i18n/catalogs/`。不引入 i18next / Lingui。`t(key, vars)` 给组件和 `libraryApi` 内存错误用。英文目录必须与中文键对齐，由测试锁定。
3. **写作协议标识保持中文**：
   - 思考槽位写入仍是 `意图：` / `约束：` / `手法：` / `兑现：` / `禁止：`
   - `@` 标签的 `tagKind` 仍是 `人物` / `伏笔` / `地点` / `道具` / `势力` / `规则`
   - 示例章《雾港来客》仍是中文样稿
   - 匹配引擎停用词与命中原因字符串仍按中文稿匹配（命中原因目前不随界面语言翻译）
4. **界面显示可以翻译**：按钮、空状态、设置、插件/工作流的展示名。打包插件清单和 MIT 工作流模板里的中文名字仍是元数据；UI 按 id 覆盖一层文案。
5. **宿主 Rust 错误串、开发者日志、手册/ADR** 这一轮不翻译。桌面 IPC 的 `error` 字段仍可能是中文。

## 后果

- 加语言：复制一份 catalog、加入 `LOCALES`、补测试。不要在 JSX 里新写用户可见字符串。
- 英文界面里 `@` 补全仍能用中文种类（`人`）或英文别名（`char`）过滤；插入后存储的仍是协议种类。
- 预选条命中原因、后端错误、日志面板里的 `logger` 消息在英界面下仍可能是中文。若以后要译命中原因，应先改成结构化 code，再在 UI 里 `t()`，并同时改 `crates/context-hints`。
